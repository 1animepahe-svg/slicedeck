# SliceDeck private Render companion (separate project)

A single-process YouTube-to-MP4 companion, not a public downloader. It is independent of the existing SliceDeck source. It is not deployed or connected to the existing GitHub Pages frontend. The existing frontend does not send the required bearer token; a separate frontend change is needed before it can use this service. This repository alone is not an installable mobile app.

## Deployment

1. Put this directory in a separate GitHub repository (or configure the Render root directory to this folder). Do not put your token in Git, the Dockerfile, client source, URLs, documentation, issue reports, or logs.
2. In Render create a **Docker Web Service**, choose the repository/root directory and **Free** compute. Use exactly **one instance/process**. Let Render supply `PORT`; the server listens on `0.0.0.0:$PORT`. Do not add a persistent disk or change to paid hosting without separately checking price and asking the owner. Free compute and bandwidth restrictions apply; see https://render.com/docs/free and https://render.com/pricing.
3. In Render's private Environment settings create `SLICEDECK_API_TOKEN`, a freshly generated, unpredictable URL-safe token from 32 or more random bytes. For example generate it on a trusted machine using Python `secrets.token_urlsafe(32)` and paste the output directly into Render's environment UI. Do not use an example or shared password. The server refuses to start unless the value contains 43–128 ASCII URL-safe letters, digits, `_` and `-`; the length check cannot establish randomness. Never commit or send the token to a public place. Rotate it in Render immediately if exposed; update the client afterward. Restart/redeploy to apply.
4. Deploy. Render terminates HTTPS; access the service only through its HTTPS public URL. The built-in Python server is not itself TLS-capable and must not be exposed separately over plain HTTP. The Docker service runs as an unprivileged user. Docker image builds, production hosting, and actual Render network/CPU behavior have not been verified here.
5. Adapt the trusted existing Pages app to accept the service URL and token privately and attach `Authorization: Bearer <token>` on every API request, with `Content-Type: application/json` for POST. Do not put the token in the static source, GitHub secrets exposed to builds, URLs or logs. Prefer entering it at runtime and keeping it in memory only; a page reload then requires reentry. Anyone with access to that page's JavaScript, the same origin, an infected device, or the token can use the service. CORS is not authentication. Only `https://1animepahe-svg.github.io` is accepted as Origin (the whole origin, not just the SliceDeck path). Bearer auth protects all non-preflight endpoints.

## API

All request paths are exact, without query strings. Browser preflight is unauthenticated but requires exactly the allowed Origin; all other requests require exactly one allowed `Origin` and one `Authorization: Bearer <token>`. Direct clients must include the Origin too (it is forgeable, hence the token). Responses include `Cache-Control: no-store`, and CORS is returned only to the allowed Origin.

* `OPTIONS /api/health` or `/api/clip`: allowed Origin; `Access-Control-Request-Method` GET for health or POST for clip; request headers may only be `authorization, content-type`. Returns 204 with CORS. No token required for preflight.
* `GET /api/health`: authenticated; returns `200 application/json` e.g. `{ "ok": true, "yt_dlp": true, "ffmpeg": true }`.
* `POST /api/clip`: authenticated, `Content-Type: application/json`, max body 4096 bytes and exactly one Content-Length, no transfer encoding. JSON keys (no extras):
  `{"url":"https://youtu.be/VIDEO_ID","start":0,"end":10,"format":"mp4","quality":"1080"}`
  `start`/`end`: finite numeric seconds, 0 <= start < end <= 14400, max 120 seconds. Quality must be the string `"720"` or `"1080"`; format must be `"mp4"`. Links must be HTTPS, an accepted YouTube hostname, no credentials/custom port, and a single valid 11-character video ID. All other URL parameters are discarded. Source must have known duration <= 4 hours, be non-live and publicly accessible without cookies, login or age verification.
* Success: `200 video/mp4`, fixed attachment filename `slicedeck-clip.mp4` and content length. H.264 video, optional AAC audio, no upscaling; maximum 1920x1080 landscape or 1080x1920 portrait at 1080, and 1280x720/720x1280 at 720. Output is checked for a video stream, frame count, dimensions, and minimum duration. A lower source resolution stays lower. Trimming/transcoding is not guaranteed frame-accurate. Download is synchronous, not a persistent job or resume endpoint; the client must wait and save the response. If the browser disconnects, work may continue to its timeout.
* Errors: `application/json` with `{ "error": "..." }`; 400 invalid data, 401 missing/wrong token, 403 origin/preflight rejected, 404 unknown path, 413 body/storage limit, 415 wrong content type, 429 busy or rate/quota limit, 500 unexpected error, 502 download/transcode/incomplete output, 503 missing tools, 504 processing timeout. Output and diagnostics are not retained. Failed jobs consume quota.

## Limits and security notes

* One active job per process, up to 3 started jobs per rolling hour and 8 per rolling 24 hours; 100 total requests/minute and at most 16 live connection threads. These are in-memory **per-instance** limits, not durable billing controls: process restarts, Render spin-down and redeploy reset them. Do not scale instances. Attacks may deny service or consume quota. No billing/bandwidth cap is provided by this code; review Render's current limits and possible charges yourself.
* 80-second shared download/transcode deadline plus up to 5 seconds for output validation, capped 96 MiB output, hard Linux 128 MiB per-file limit inherited by tools, and a polled 192 MiB job-directory ceiling. The directory cap can overshoot between checks; yt-dlp `--max-filesize` is not a hard network-byte limit and media transfers can exceed it. There is no bandwidth cap. Process-group kill, timeouts, low thread counts and a 15-second socket timeout reduce exposure, not eliminate it. Render imposes container memory/CPU limits; a 512 MiB container can still be OOM-killed. The Linux per-file limit is set in the main entry point and inherited by children; direct calls to library functions in tests do not set it.
* Temporary job files are cleaned after success, failure, or disconnection; stale workspace is removed at next startup. Hard kills can leave files until restart; Render's filesystem is ephemeral. Do not store sensitive videos on a service you do not trust. Requests, URL and token are not deliberately logged by this application, and child processes receive a minimal environment without the token; hosting provider/proxies may have their own logs.
* The server accepts only canonicalized YouTube IDs; no user-chosen arbitrary URL, shell command, cookies, or credentials are passed to downloaders. yt-dlp still contacts upstream media hosts and parses untrusted media; no network firewall prevents all internal-address access, and media parser vulnerabilities are possible. Keep the image, Python packages, yt-dlp, Node and ffmpeg patched, and consider container isolation/egress filtering. No absolute security guarantee.
* YouTube may block cloud-provider IPs or require login/challenges. It can break yt-dlp at any time; dependencies need review and updates. Use only videos you have rights to process and comply with applicable platform terms. No promise of bypassing restrictions.
* Render Free spins down and wakes slowly. It may restart, discard temporary state, rate-limit, OOM or fail slow 1080p jobs; CPU and outbound limits are tight. Large/high-quality videos often will not finish in 80 seconds. No paid fallback, cookies or YouTube login is configured.

## Local tests

Linux Python 3.11+ with ffmpeg/ffprobe: `python -m unittest -v test_server.py`. Tests exercise authentication, origin/preflight, request and job limits, validation, temporary cleanup, timeout, and synthetic H.264 1080p/720p output. The project depends on the pinned `yt-dlp[default]` release, ffmpeg and Node. This directory's tests are independent of the original SliceDeck tests.
